# Ctron 语言介绍

## 为什么写 Ctron

写一个 hello world 需要装一套 2GB 的工具链；改一行代码要等 40 秒链接；发布产物依赖二十个动态库——这些是 C/C++ 生态的日常。换 Go/Rust 能解决大部分问题，但又引入了新的：语言自带的运行时、黑盒标准库、编译器"帮你"做的隐式决定。

Ctron 想要的是：**脚本语言的迭代速度，系统语言的生产质量，中间没有断层。**

具体来说：

- 改完代码立刻能跑（`ctc run`），不需要编译等待；
- 部署时同一个文件发射为 C，交给本机编译器出原生二进制（`ctc build`）；
- 解释路径零外部依赖——没有 C 工具链的机器也能跑；
- 发射产物自包含——运行时全部内联，不依赖动态库。

两条执行路径服务于同一个开发周期：写代码用解释路径快速迭代，上线前切原生口径出产物。不存在"开发用脚本语言、生产用另一种语言重写"的断层。

## 自举

Ctron 的编译器全部用 Ctron 写成。这不是炫技——自举是语言设计最严格的测试：如果语言缺少某个能力，编译器自己就写不出来；如果标准库缺某个函数，编译器一调就暴露。

自举的交付物是逐字节确定性：不同平台发射出的 C 编译出的编译器，再发射出的 C **逐字节相同**。这作为发布承诺进 CI，不是文档里的一句话。

自举同时意味着标准库可读——标准库是 Ctron 源码，不是编译好的二进制。`use std.*` 在编译期读源码、与程序合并为单一 AST。想看 `List` 怎么实现？打开文件看。想改？改完自己用。

## 设计取向

### 静态安全，不靠仪式

Ctron 用 `Option` / `Result` 替代空指针和异常，用 `?` 做错误传播，用 `Error` trait 做错误链。没有 null，没有隐式类型转换，没有未定义行为的隐式触发。

不采用 Rust 的借用检查。Ctron 的内存模型是 GC + RAII + `own` 块的三层设计：默认 GC 管理生命周期，RAII 处理确定性释放，`own` 块提供无 GC 的作用域子集。不需要提前想清楚每一块内存的所有权——需要确定性的时候再显式标注。

### 结构化并发，不用线程池

任务跑在 `scope` 之下——块作用域管理，取消沿 scope 传播。不需要手动管理线程生命周期，也不会有线程泄漏。`Send` 检查在编译期完成，不需要运行时竞态检测。

### 诊断即契约

每个错误带稳定错误码（E2010、W8050…），不是模板拼接的万行报错。`ctc check --format=json` 出结构化诊断，给编辑器和 CI 消费。诊断的文案可以改，错误码不改——工具链升级不破坏已有 CI 规则。

### C 是后端，不是祖先

Ctron 发射 C，但不用 C 的方式思考。发射产物是自包含的 C 源码——运行时全部内联，只包含系统头文件。有 cc 的平台就是目标平台。C 生态的库经 FFI 可用（`extern "c"` + `#[trusted]`），但不需要用 C 的方式管理内存。

## 语言与工具链的关系

Ctron 把"语言"和"工具链"分开。语言版本描述语法和语义；工具链版本描述实现质量。`ctc` 是唯一入口，三个子命令覆盖开发周期：

```
ctc run     开发迭代
ctc check   静态检查
ctc build   出生产产物
```

不需要记住编译器 flag、链接器选项、目标三元组——`ctc` 帮你选好。需要更细控制时，`Ctron.toml` 覆盖默认。

## 适用场景

Ctron 适合写需要系统级控制但不想用 C 的程序：CLI 工具、网络服务、编译器、解析器。不适合写 GPU 密集计算（没有 SIMD 内建）或实时系统（GC 停顿不可控——bare 档缓解但未消除）。

如果你已经用 Go 或 Rust，Ctron 提供的是更小的语言面 + 零依赖解释执行 + C 发射后端。如果你用 C，Ctron 提供的是错误处理 + 结构化并发 + 无 UB。如果你用 Python，Ctron 提供的是静态类型 + 原生性能——但迭代速度会慢一些。
