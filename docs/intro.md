# Ctron：AI Native 系统编程语言

Ctron 从设计之初就以 AI 生成代码为主要使用方式。这不是事后适配——语言的语法、类型系统、错误模型、诊断格式，每一层都围绕"AI 写、人审"这个前提做出取舍。

## 为什么需要 AI Native 的语言

AI 生成的代码有一个稳定特征：结构正确，细节出错。变量名拼错、类型不匹配、遗漏边界条件、用了不该用的 API。这些错误在动态语言里往往要到运行时才暴露，在 C/C++ 里可能直接变成未定义行为。

AI Native 的语言把这类错误挡在编译期。手段不是"更好的 AI"，而是更严格的语言设计：

- **每个错误带稳定错误码**（E2010、W8050…）。AI 收到错误码后可以精确修正，不需要从自然语言描述中猜意图。
- **诊断结构化输出**（`ctc check --format=json`），给编辑器和 CI 管道消费，不依赖正则提取。
- **类型推断有明确规则**（§3.9 两段式），AI 写出的类型标注即使多余也不会引入错误。
- **语法歧义在规范中逐条钉死**（§1.8 消歧规则），AI 不会因为解析不确定而生成不同结构的代码。

## 没有魔法

AI 写代码最怕的不是语法复杂，而是语言在暗处做了什么。隐式类型转换让 AI 以为自己在操作一个类型，实际是另一个；运算符重载让 `+` 在不同类型上行为不同；宏展开让源码和实际执行的代码不一致。

Ctron 的规则：

- 无 null——用 `Option[T]`。
- 无隐式数值转换——`I32` 不会自动变 `I64`。
- 无运算符重载——`+` 就是加法。
- 无宏——没有语法层面的文本替换。
- 无未定义行为——规范逐条列出所有合法行为，没写的就不存在。

标准库是 Ctron 源码，不是编译好的二进制。`use std.*` 在编译期读源码、与程序合并为单一 AST。AI 可以读标准库源码来理解 API 行为，不需要查文档。

## 语义清晰，所见即所意

代码做了什么，就是它看起来的样子。一个赋值语句不会触发构造函数、析构函数或自定义运算符。`fn` 声明函数，`struct` 声明数据，`impl` 声明方法，没有 `class` 同时做三件事的设计。

`?` 做错误传播——替代 `match err { Ok(v) => v, Err(e) => return Err(e) }`，语义不变，代码更短。

`scope` 做结构化并发——任务跑在块作用域之下，取消沿 scope 传播，`Send` 检查在编译期完成。不需要手动管理线程生命周期。

## 简洁

在清晰无歧义的前提下，完成同一个任务需要的概念数量最少。

语法构造只做一件事：`fn` 声明函数，`struct` 声明数据，`impl` 声明方法。没有 `class` 同时做三件事的设计。没有 `trait` + `impl` + `where` + `lifetime` 的组合拳。

## 编译器用 Ctron 写

Ctron 的编译器全部用 Ctron 写成。自举证明语言能写真实软件，同时让编译器源码成为语言能力的最严格测试。

自举的交付物是确定性：不同平台发射出的 C 编译出的编译器，再发射出的 C 逐字节相同。

标准库是 Ctron 源码。`use std.*` 在编译期读源码、与程序合并。AI 可以读标准库源码理解 API，不需要查文档。

## 两条执行路径

```
ctc run main.ct      解释执行，不需要 C 工具链
ctc build main.ct    发射 C → 本机 cc → 原生可执行
```

解释路径零外部依赖。发射路径自包含——运行时全部内联，只含系统头文件。同一份源码，开发和部署不换语言。

## 适用场景

CLI 工具、网络服务、编译器、解析器。

不适合 GPU 密集计算（无 SIMD 内建）或硬实时系统（GC 停顿不可控——bare 档缓解但未消除）。
