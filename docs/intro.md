# Ctron 语言介绍

## 设计原则

Ctron 的语言设计遵循一条主线：

> AI 写，人类读。语义清晰，所见即所意。没有隐藏，没有魔法。在表达清晰无歧义的前提下，尽可能简洁。

这条主线决定了每一个语言层面的取舍。下面逐条说明它意味着什么，以及 Ctron 用什么方式实现它。

### AI 写，人类读

越来越多代码由 AI 生成。AI 生成的代码有一个特征：结构正确，但细节可能出错——变量名拼错、类型不匹配、遗漏边界条件。语言和工具链的职责是让这些错误在编译期暴露，而不是在运行时才发现。

这意味着：

- 每个错误带稳定错误码（E2010、W8050…），不是模板拼接的万行报错。AI 可以根据错误码精确修正。
- 类型推断有明确规则（§3.9），不是猜。AI 写出的类型标注即使多余也不会错。
- 诊断输出结构化（`ctc check --format=json`），给编辑器和 CI 消费。

对人类读者同样成立：代码结构正确但逻辑有错时，静态检查能抓到的就抓。

### 语义清晰，所见即所意

代码做了什么，就是它看起来的样子。没有隐式类型转换，没有运算符重载，没有宏展开改变语法，没有编译器"帮你"插入的代码。

具体禁令：

- 无 null——用 `Option[T]` 替代。
- 无隐式数值转换——`I32` 不会自动变 `I64`，需要显式 `.as[I64]()`。
- 无运算符重载——`+` 就是加法，不会因为类型不同而变成拼接或合并。
- 无宏——没有语法层面的文本替换。
- 无未定义行为——语言规范逐条列出了所有合法行为，规范没写的就是不存在的。

### 没有魔法

标准库是 Ctron 源码，不是编译好的黑盒。`use std.*` 在编译期读源码、与程序合并为单一 AST。想看 `List` 怎么实现？打开文件看。想改？改完自己用。

编译器也是 Ctron 写的。自举不是炫技——如果语言缺少某个能力，编译器自己就写不出来。三级自举固定点已脚本化复现：不同平台发射出的 C 逐字节相同。

### 在清晰的前提下尽可能简洁

简洁不是省略关键字。简洁是：完成同一个任务需要的概念数量最少。

- `?` 做错误传播，不需要写 `match err { Ok(v) => v, Err(e) => return Err(e) }`。
- `scope` 做结构化并发，不需要手动管理线程生命周期。
- `use` 做模块导入，不需要写头文件守卫或 `__init__.py`。

每个语法构造只做一件事。`fn` 声明函数，`struct` 声明数据，`impl` 声明方法。没有 `class` 同时做三件事的设计。

## 两条执行路径

同一份 Ctron 源码，两条执行路径：

```
ctc run main.ct      解释执行，不需要 C 工具链
ctc build main.ct    发射 C → 本机 cc → 原生可执行
```

解释路径用于开发迭代：改完代码立刻能跑，不需要编译等待。发射路径用于部署：同一个文件出原生二进制。不存在"开发用脚本语言、生产用另一种语言重写"的断层。

解释路径零外部依赖——没有 C 编译器的机器也能跑。发射路径自包含——运行时全部内联，只含系统头文件。有 cc 的平台就是目标平台。

## 编译器用 Ctron 写

Ctron 的编译器全部用 Ctron 写成。自举是语言设计最严格的测试：如果语言缺少某个能力，编译器自己就写不出来；如果标准库缺某个函数，编译器一调就暴露。

自举的交付物是确定性：不同平台发射出的 C 编译出的编译器，再发射出的 C 逐字节相同。这作为发布承诺进 CI。

标准库是 Ctron 源码，不是编译好的二进制。`use std.*` 在编译期读源码、与程序合并为单一 AST。想看 `List` 怎么实现？打开文件看。想改？改完自己用。

## 适用场景

Ctron 适合写需要系统级控制但不想用 C 的程序：CLI 工具、网络服务、编译器、解析器。

不适合写 GPU 密集计算（没有 SIMD 内建）或硬实时系统（GC 停顿不可控——bare 档缓解但未消除）。

如果你已经用 Go 或 Rust，Ctron 提供的是更小的语言面加零依赖解释执行加 C 发射后端。如果你用 C，Ctron 提供的是错误处理加结构化并发加无 UB。如果你用 Python，Ctron 提供的是静态类型加原生性能——但迭代速度会慢一些。
